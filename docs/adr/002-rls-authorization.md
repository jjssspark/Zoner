# ADR-002 — 권한을 앱 코드가 아니라 DB(RLS)에서 막는다

**날짜** 2026-08-04 · **상태** 채택 · **관련** [DATABASE.md](../DATABASE.md), [API.md](../API.md)

## 맥락

Zoner의 데이터는 전부 개인 소유다 — 프로필, 세션 기록, 채팅, 녹화 영상.
남의 것이 보이면 안 된다는 요구가 테이블 4개와 Storage 버킷 1개 전부에 똑같이 걸린다.

구조상 중요한 사실이 하나 있다. **브라우저가 Supabase에 직접 붙는다.**
중간에 내 서버가 없다. 브라우저가 들고 있는 것은 anon 키이고, 그 키로 `study_sessions`를
그대로 조회할 수 있다.

## 선택지

| 안 | 내용 | 문제 |
|---|---|---|
| A. 앱 코드에서 필터 | 모든 쿼리에 `.eq('user_id', user.id)`를 붙인다 | **클라이언트 코드는 사용자가 고칠 수 있다.** 조건을 빼고 요청하면 그만이다 |
| B. API 서버 경유 | 모든 DB 접근 앞에 내 서버를 둔다 | 서버 하나를 만들고 띄우고 유지해야 한다 |
| C. RLS | Postgres 행 수준 보안 정책으로 DB가 직접 막는다 | 정책이 SQL에 있어 앱 코드 리뷰에서 안 보인다 |

## 결정

**C — 모든 테이블과 Storage 버킷에 RLS를 켜고 정책 17개를 건다.**

기준은 세 가지뿐이다.

```sql
auth.uid() = id                                      -- profiles
auth.uid() = user_id                                 -- study_sessions, conversations, chat_messages
(storage.foldername(name))[1] = auth.uid()::text     -- session-videos 버킷
```

## 근거

**A는 애초에 안전장치가 아니다.** 브라우저가 DB에 직접 붙는 구조에서 클라이언트의 `where` 절은
보안 경계가 아니라 편의 기능이다. 공격자가 코드를 고치는 게 아니라, DevTools 콘솔에서
`supabase.from('study_sessions').select('*')`를 치면 끝난다.

**B는 이 규모에서 비용이 이득을 넘는다.** 인증 서버를 직접 만들 이유가 없어서 Supabase를 골랐는데,
권한 때문에 다시 서버를 세우면 고른 이유가 사라진다.

**C는 실수해도 새지 않는다.** 앱 코드에서 소유자 조건을 빠뜨려도 DB가 빈 결과를 준다.
버그가 "데이터가 안 보인다"로 나타나지 "남의 데이터가 보인다"로 나타나지 않는다.
**실패 방향이 안전한 쪽인 것**이 이 결정의 핵심이다.

## 대가

**Edge Function은 이 보호 밖에 있다.** 두 함수 모두 `SUPABASE_SERVICE_ROLE_KEY`로 클라이언트를
만들기 때문에 RLS를 우회한다. 그래서 `ai-chat`은 대화 소유자를 **코드가 직접** 비교한다.
"DB가 막아 준다"는 전제가 여기서만 깨지는데, 그걸 잊으면 그대로 구멍이 된다.

**뷰에는 `security_invoker = true`가 필요하다.** 이 플래그가 있어야 뷰가 호출자 권한으로 평가돼
아래 테이블의 RLS가 그대로 걸린다. `active_study_sessions`에 이 옵션이 붙어 있는 이유다.

**`update` 정책에는 `using`과 `with check`를 둘 다 걸어야 한다.** `using`만 걸면 자기 행을 읽어서
`user_id`를 남의 것으로 바꿔 쓰는 것을 막지 못한다.

**정책은 코드 리뷰에 안 보인다.** 마이그레이션 SQL 안에 있어서, JS만 읽는 리뷰에서는 존재 자체가 안 보인다.

## 결과

정책 자체로 인한 데이터 유출은 없었다. 대신 RLS가 **다른 층에서 부작용**을 냈다.

`Mypage`가 스켈레톤 상태로 영구히 멈춘 적이 있는데(TROUBLESHOOTING.md TS-008),
원인은 뷰에 `HEAD` + `count=exact` 요청을 건 것이 503을 내고 그 실패가 로딩 해제에 도달하지
못한 것이었다. 권한 자체는 정상이었지만, **테이블이 아니라 뷰를 거치는 구조**가 원인의 한 축이었다.

돌아보면 대가 목록 중 실제로 물린 것은 "Edge Function이 보호 밖에 있다" 하나다.
그건 함수를 처음 쓸 때 알았고 코드에 경고 주석으로 박아 뒀다.

되돌릴 이유는 없다. 오히려 정책 수가 늘어날수록 이 구조의 이득이 커진다 —
새 테이블을 추가할 때 "권한 코드를 어디에 넣지"를 고민할 필요가 없다.
