# ADR-001 — 얼굴 추론을 서버가 아니라 브라우저에서 돌린다

**날짜** 2026-08-04 · **상태** 채택 · **관련** [ADR-005](005-ci-false-over-craco.md)

## 맥락

집중도를 재려면 학습 중 웹캠 영상에서 얼굴 랜드마크를 뽑아야 한다.
판정 주기는 5초, 세션은 보통 30분~2시간이다. 즉 **세션 하나에 수백~수천 프레임**을 다뤄야 한다.

그리고 그 프레임은 사용자의 얼굴이다. 방 안 배경까지 함께 찍힌다.

## 선택지

| 안 | 내용 | 문제 |
|---|---|---|
| A. 서버 추론 | 프레임을 서버로 보내 추론 | 영상이 기기 밖으로 나간다. 전송 지연 + GPU 서버 비용 |
| B. 브라우저 추론 | MediaPipe Tasks Vision을 WASM+GPU로 실행 | 모델·런타임을 런타임에 받아야 한다 |
| C. 자체 모델 학습 | 데이터 수집 + 학습 + 서빙 | 일정 안에 불가능 |

## 결정

**B — MediaPipe FaceLandmarker를 브라우저에서 실행한다.**

서버로 올라가는 것은 5초마다 한 번 나오는 **판정 결과**(집중 여부와 사유)뿐이다.
프레임은 `getUserMedia` → `<video>` → MediaPipe → `focusTracker` 안에서 끝난다.

세션 녹화 영상은 예외인데, **사용자가 명시적으로 켰을 때만** 비공개 Storage 버킷에 올라간다.

## 근거

**민감한 데이터는 옮기지 않는 게 가장 싸다.** 프레임을 서버로 보내는 순간 전송 구간 보호,
저장 여부, 보관 기간, 삭제 요청 처리가 전부 내 책임이 된다. 개인 프로젝트에서 그걸 제대로
할 자신이 없었고, 제대로 못 할 거면 아예 받지 않는 편이 낫다.

**지연이 기능의 성격을 바꾼다.** "실시간 집중도"인데 왕복이 붙으면 실시간이 아니다.
브라우저 안에서는 추론이 프레임 파이프라인에 붙어 있어 왕복 자체가 없다.

**자체 학습은 이 프로젝트의 문제가 아니다.** MediaPipe는 랜드마크·블렌드셰이프·머리 회전
행렬을 한 번에 주므로, 내가 만들어야 하는 것은 **"그 값을 어떻게 집중/비집중으로 읽을 것인가"**
하나로 좁혀진다. 그게 이 앱의 진짜 설계 문제다 — 6개 판정 상태와 임계값이 거기서 나왔다.

## 대가

**외부 CDN 두 곳에 런타임 의존한다.** jsdelivr(WASM 런타임)와 Google Storage(모델 가중치)에서
최초 1회 받아 온다. **오프라인에서는 측정이 시작되지 않는다.** 실서비스라면 자가 호스팅 대상이다.

**기기 성능이 곧 판정 품질이다.** 저사양 기기에서 5초 주기를 못 따라가면 샘플이 빠진다.

**1인 기준이다.** `numFaces: 1`이라 여러 명이 잡히는 환경은 고려하지 않았다.

## 결과

의도한 것은 그대로 됐다. 서버는 판정 결과만 받고, 프레임은 브라우저 경계를 넘지 않는다.

**예측하지 못한 비용이 하나 청구됐다.** `@mediapipe/tasks-vision`의 `vision_bundle.mjs`가
웹팩이 정적 분석할 수 없는 동적 import 표현식을 쓴다. 로컬에서는 경고로 끝나지만,
`CI=true`를 자동으로 거는 배포 환경에서는 CRA가 그 경고를 에러로 승격해 **빌드가 통째로 실패했다**
(TROUBLESHOOTING.md TS-020). 3주 가까이 로컬 검증을 전부 통과한 코드가 첫 배포에서 즉시 깨졌다.

라이브러리를 패치하지 않는 한 없앨 수 없어서, 결국 빌드 쪽에서 우회했다 → [ADR-005](005-ci-false-over-craco.md).

**"의존성을 하나 고르는 것은 그 라이브러리의 빌드 특성까지 고르는 것"**이라는 게
이 결정에서 실제로 배운 부분이다. 추론 품질과 라이선스는 봤지만 번들러 호환성은 보지 않았다.

되돌릴 이유는 아직 없다. 되돌린다면 그건 성능이 아니라 **오프라인 지원**이 필요해질 때다.
