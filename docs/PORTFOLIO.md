# Zoner — 포트폴리오 설명문

## 문제 정의

공부한 **시간**은 어디서나 기록된다. 타이머 앱, 스터디 플래너, 학습 관리 서비스가 전부 그걸 해준다.
그런데 **"그 시간에 실제로 집중했는지"**는 아무도 알려주지 않는다.
3시간 앉아 있었다는 기록은, 그중 40분을 멍하니 보냈다는 사실을 지운다.

Zoner는 학습 중 웹캠 영상을 **브라우저 안에서만** 분석해 5초마다 집중 여부를 판정하고,
세션이 끝나면 언제 무너졌는지·무엇이 방해했는지를 파생 지표 9종으로 돌려주는 React 웹앱이다.

**▶ https://zoner-one.vercel.app** · 소스: [`README.md`](../README.md)

만든 기간은 2026-08-04 ~ 08-11, 8일이다. 그 안에서 기능을 늘리는 것보다
**"판단이 갈린 지점마다 근거를 남기고, 검증이 실제로 무엇을 재현했는지 따지는 것"**에 시간을 썼다.

## 기술적 의사결정

### 1. 영상을 서버로 보내지 않는 쪽을 골랐다

집중도 판정에는 얼굴 랜드마크가 필요하다. 선택지는 프레임을 서버로 보내 추론하거나,
브라우저에서 직접 돌리거나 둘이었다.

**브라우저를 골랐다.** MediaPipe FaceLandmarker를 WASM+GPU로 실행한다.
서버로 올라가는 것은 5초마다 한 번 나오는 판정 결과(집중 여부와 사유)뿐이고,
**웹캠 프레임은 브라우저 경계를 넘지 않는다.**

민감한 데이터는 옮기지 않는 게 가장 싸다는 판단이었다. 프레임을 서버로 보내는 순간
전송 구간 보호·보관 기간·삭제 요청 처리가 전부 내 책임이 되는데, 개인 프로젝트에서
그걸 제대로 할 자신이 없었다. 제대로 못 할 거면 아예 받지 않는 편이 낫다.

**대가도 실제로 왔다.** MediaPipe의 WASM 런타임과 모델 가중치를 외부 CDN에서 받아 오므로
오프라인에서는 측정이 시작되지 않는다. 그리고 그 라이브러리가 웹팩이 정적 분석할 수 없는
동적 import를 써서, 나중에 **첫 배포를 통째로 깨뜨렸다**(아래 5번).
의존성을 하나 고르는 것은 그 라이브러리의 빌드 특성까지 고르는 것이었다.

→ [ADR-001](adr/001-in-browser-inference.md)

### 2. 오판의 방향을 정했다 — 잘못 칭찬하는 쪽으로

얼굴만 보는 모델로는 **교재를 보는 것과 휴대폰을 보는 것을 구분할 수 없다.**
`looking_down`(고개 숙임)을 집중으로 셀지 비집중으로 셀지를 정해야 했다.

집중으로 세기로 했다. **공부 중인 사용자를 딴짓으로 오판하는 쪽이 반대 방향 오차보다 비용이 크다**고 봤다.
잘못 칭찬하면 넘어가지만, 잘못 혼내면 앱을 끈다.

같은 성격의 판단이 두 개 더 있다.

- **눈 감김은 연속 2회일 때만 졸음으로 본다.** 깜빡임은 0.1~0.4초다. 5초 샘플링으로는 한 번에 구분할 수 없어서, 샘플링 주기를 줄이는 대신 연속성 조건을 붙였다 — 배터리와 발열을 덜 쓰는 쪽
- **리포트의 "무너짐" 판정에서 앞 2분을 뺀다.** 카메라가 얼굴을 잡고 자세를 잡는 구간이라 거의 모든 세션이 0분에서 낮게 찍힌다. 그대로 세면 "집중 지속 한계 약 0분" 같은 뜻 없는 값이 나온다. 워밍업은 이탈이 아니다

화면에 띄우는 숫자도 누적 평균이 아니라 **최근 2분 이동 창**의 집중률이다.
누적 평균은 세션이 길어질수록 둔해져서, 30분쯤 지나면 고개를 들어도 숫자가 거의 안 움직인다.

### 3. 권한을 앱 코드가 아니라 DB에서 막았다

브라우저가 Supabase에 직접 붙는 구조다. 중간에 내 서버가 없다.
이 구조에서 클라이언트의 `where user_id = ...`는 **보안 경계가 아니라 편의 기능**이다.
코드를 고칠 필요도 없이 DevTools 콘솔에서 조건 없는 쿼리를 치면 그만이다.

그래서 테이블 4개와 Storage 버킷 전부에 RLS를 켜고 **정책 17개**를 걸었다.
기준은 `auth.uid() = user_id`(Storage는 경로 첫 세그먼트 비교) 하나뿐이다.

핵심은 **실패 방향이 안전한 쪽**이라는 것이다. 앱 코드가 소유자 조건을 빠뜨리면
버그가 "데이터가 안 보인다"로 나타나지 "남의 데이터가 보인다"로 나타나지 않는다.

이 구조에는 예외가 하나 있고, 그걸 아는 것이 중요하다. **Edge Function은 이 보호 밖에 있다.**
`SUPABASE_SERVICE_ROLE_KEY`로 만든 클라이언트는 RLS를 우회하므로,
`ai-chat`은 대화 소유자를 코드가 직접 비교한다. 그리고 **존재하지 않는 대화와 남의 대화를
같은 404로 돌려준다** — 다르게 응답하면 UUID를 넣어 보는 것만으로 존재 여부를 알아낼 수 있다.

→ [ADR-002](adr/002-rls-authorization.md) · [DATABASE.md](DATABASE.md)

### 4. AI에게 통계를 시키지 않았다

리포트에 조언 문단이 붙는다. 여기서 갈린 지점은 "모델에게 무엇을 주느냐"였다.

**수치는 전부 앱이 계산해 넘기고 모델은 읽기만 한다.** 순 집중 시간, 최장 지속, 첫 이탈 시점,
전·후반 격차, 변동성(모표준편차), 시간당 알림, 최대 방해 원인 — 9종 전부 `src/lib/`에서 계산한다.
모델에게 원본을 주고 세라고 하면 숫자가 틀린다. 시스템 프롬프트에도
**"수치를 다시 계산하거나 고치지 않는다. 인용만 한다"**를 박아 뒀다.

그 결과 추론 난도가 낮아져서 `claude-haiku-4-5`로 충분했다. 응답 속도와 비용이 더 중요했다.

**Edge Function은 클라이언트가 보낸 본문을 신뢰하지 않는다.**
숫자는 `Number()`로 강제 변환해 `Number.isFinite()`를 통과한 것만 쓰고,
라벨은 허용 목록 6종(`focused`·`looking_down`·`head_turned`·`looking_up`·`eyes_closed`·`absent`)으로만 받는다.
통과하지 못한 필드는 **프롬프트 줄 자체를 만들지 않는다.** 그대로 이어붙이면 조작된 클라이언트가
지시문을 심을 수 있는데, 허용 목록 방식이면 심을 수 있는 게 상수 6개뿐이다.

표본이 모자라면 학습 성향을 **아예 보내지 않는다.** 근거가 약한 값을 주면 모델은 그걸로
단정적인 문장을 만든다. 그리고 조언 생성이 실패해도 **리포트는 죽지 않는다** —
조언 섹션만 접고 나머지 지표는 그대로 보여준다. AI는 부가 요소이지 전제가 아니다.

→ [API.md](API.md)

### 5. 배포가 여태 없던 검증 계층이었다

3주 가까이 쌓은 코드가 로컬 검증을 전부 통과한 상태에서 첫 배포를 시도했고, **즉시 깨졌다.**

원인이 두 겹이었다. CI 환경은 `CI=true`를 자동으로 걸고, CRA는 그걸 보면 경고를 에러로 승격한다.
그리고 승격된 그 경고는 우리 코드가 아니라 `@mediapipe/tasks-vision`에서 나왔다.
**에러 메시지는 "의존성이 이상하다"고 말하는데 실제로 고쳐야 할 것은 빌드 환경변수였다.**

더 중요한 건 **왜 배포 전에 못 잡았는가**다. 구현 계획의 완료 기준이
`npx react-scripts build` 성공이었는데, **이 명령은 CI 조건을 재현하지 않는다.**
로컬 셸에 `CI`가 없으니 승격이 일어나지 않고, 따라서 이 검증은 통과할 수밖에 없었다.
**실패할 수 없는 조건으로 짜인 검증이었다.**

해결은 `vercel.json`의 빌드 명령에만 `CI=false`를 걸었다. CRACO를 도입해 그 경고만 골라 끄는
방법도 있었지만, 서드파티 경고 하나 때문에 새 빌드 의존성을 얹는 비용이 더 크다고 봤다.
`CI=false`는 **우리 코드의 lint 경고까지 함께 눈감아 준다 — 대가를 알고 고른 선택이다.**
`@mediapipe/tasks-vision`을 올려 경고가 사라지면 걷어내는 것이 되돌리는 조건이다.

그리고 결정보다 중요한 후속 조치를 했다 — **완료 기준의 빌드 검증을 `CI=true`로 바꿨다.**

→ [ADR-005](adr/005-ci-false-over-craco.md)

### 6. 도구 제약이 코드 구조를 밀어냈다

CRA 번들 Jest 리졸버가 `react-router-dom` v7의 exports 맵을 해석하지 못한다.
**`react-router-dom`을 import 하는 파일에는 테스트를 쓸 수 없다**는 뜻이다.

그래서 판단이 들어간 순수 로직은 `src/lib/`으로, 라우터에 의존하지 않는 프레젠테이션 컴포넌트는
`src/components/ui/`로 내려갔다. 의존은 `features/` → `components/` → `lib/` 안쪽으로만 흐른다.

관심사 분리는 좋아졌지만, **그건 설계 판단이 아니라 도구 제약이 밀어낸 결과**다.
그렇게 적어 두는 편이 정직하다. 그리고 화면 단위 E2E가 없다는 공백이 그대로 남았다.

Vite로 이전하지 않은 이유는 8일 일정에서 **사용자에게 닿지 않는 개선**이었기 때문이다.
그 판단은 유지하지만, **비용을 과소평가했다** — 이전을 미룬 대가가 개발 서버 속도가 아니라
테스트 범위와 배포 성공 여부에 왔다.

→ [ADR-003](adr/003-keep-cra.md)

### 7. 다크 단일 테마 — 예측이 절반만 맞았다

라이트/다크 양쪽을 지원하면 **전 화면 대비비를 두 벌 검증**해야 한다.
한 테마에서만도 두 번 물렸다 — `oklch()` 색의 대비비를 손계산하다 L/C/H를 R/G/B로 오독한 건(TS-006),
`--color-border-strong`이 이름과 달리 UI 경계 3:1에 미달한 건(surface 위 2.83:1, TS-016).
토큰 이름이 `strong`이라 충분해 보였는데 아니었다.

그래서 다크만 두기로 했고, 색 작업은 실제로 빨라졌다.

**틀린 부분은 "테마를 하나로 줄이면 매체도 하나"라는 전제였다.**
PDF 저장 기능을 만들면서 **인쇄**라는 두 번째 매체가 생겼다. 흰 종이 위에 찍히므로
다크 토큰이 그대로 나가면 안 되고, 결국 `@media print`에서 토큰을 오버라이드해야 했다.
그게 사실상 라이트 테마를 만드는 일이었고, 그 대가를 트러블슈팅 두 건으로 치렀다(TS-018, TS-019).

**매체는 테마보다 많다**는 걸 처음부터 알았어야 했다.

→ [ADR-004](adr/004-dark-only-theme.md)

## 무엇을 배웠나 — 검증에 대해

트러블슈팅 21건을 쌓고 나서 남은 것 중 하나로 꼽으면 이거다.

> **검증이 통과했다는 사실 자체는 아무것도 보장하지 않는다.
> 무엇을 재현한 검증인지가 전부다.**

같은 구조의 실패가 여러 번 반복됐다.

| 건 | 검증은 통과했다. 그런데 | |
|---|---|---|
| TS-017 | 측정 도구(`getComputedStyle`)가 **그 환경에서 거짓값**을 줬다 | 애니메이션이 억제된 컨텍스트에서 시작값이 나온다 |
| TS-010 | 독립 정적 리뷰 **3회가 옳은 답**을 냈는데 실행이 달랐다 | `finally`는 실제로 무조건 실행됐다. 아무도 가드의 값을 묻지 않았다 |
| TS-012 | **에러가 한 번도 안 났다.** 하루 넘게 반쪽만 살아 있었다 | 쓰기는 테이블로, 읽기는 뷰로 갈라져 아무도 부딪히지 않았다 |
| TS-020 | 검증 명령이 **실행 환경을 재현하지 않았다** | 실패할 수 없는 조건이었다 |
| TS-005 | 브라우저 실측을 **전부 통과**했다 | 전부 포그라운드였다. 문제는 백그라운드 탭에만 있었다 |
| TS-018 | 검증 하니스가 `body`에 **흰 배경을 강제**해 버그를 가렸다 | 검증 도구가 검증 대상을 우회했다 |

그래서 지금은 완료 기준을 쓸 때 **"이 검증은 실패할 수 있는가"**를 먼저 묻는다.
답이 "아니오"면 그건 검증이 아니다.

→ [TROUBLESHOOTING-TOP5.md](TROUBLESHOOTING-TOP5.md) · [TROUBLESHOOTING.md](TROUBLESHOOTING.md)

첫 화면이 그려지는데, 느린 4G를 흉내 내면 그 지연이 10.9초로 잡히고 데스크톱에서는
240 ms로 줄어든다. 코드 스플리팅이나 Vite 이전이 해법이고, 이미
[ADR-003](adr/003-keep-cra.md)에 **부채로 등록해 둔** 항목이다. 점수가 그 대가를
숫자로 확인해 줬다.

**측정할 수 있는 건 랜딩까지다.** 정작 무거운 화면(측정·리포트)은 로그인 뒤라
Lighthouse가 들어가지 못한다. 이 점수를 제품 전체의 성능으로 읽으면 안 된다.

한편 **접근성·모범 사례·SEO는 두 조건 모두 100이고, TBT 0 ms · CLS 0이다.**
브라우저에서 추론을 돌리면서도 초기 로드에서 메인 스레드를 막지 않고 레이아웃도
흔들리지 않는다.

**테스트는 커버리지 숫자를 올리는 대신 판단이 들어간 곳만 덮었다** —
집중 판정 임계값 경계, 세션 집계, 파생 지표, 알림 규칙, 학습 성향 분류,
휴지통·녹화 상태 전이, 그리고 CSS 토큰 참조 정합성.
화면 컴포넌트는 위 6번의 리졸버 제약 때문에 대상이 아니다.

**트러블슈팅 21건에는 실패한 시도를 전부 남겼다.** 틀린 가설, 못 잡은 이유,
근본 해결 대신 우회한 건까지 그대로 적었다. 고친 결과보다 그쪽이 남는 기록이라고 봤다.

## 알려진 한계

아는 것과 모르는 것을 구분하는 게 더 중요하다.

- **얼굴만 본다.** 교재를 보는지 휴대폰을 보는지 구분하지 못한다. 그래서 `looking_down`을 집중으로 세는 쪽을 택했다
- **1인 기준.** `numFaces: 1`이라 여러 명이 잡히는 환경은 고려하지 않았다
- **외부 CDN 의존.** MediaPipe WASM·모델을 런타임에 받아 오므로 오프라인에서는 측정이 시작되지 않는다
- **CRA를 유지 중.** `react-scripts` 5.0.1은 유지보수가 멈춘 상태다. 이전 비용을 알면서 남겨 둔 부채다
- **테스트가 로직에 치우쳐 있다.** 화면 단위 E2E가 없다. 리졸버 제약이 이유이지만 Playwright로 우회할 수 있는 문제이기도 하다
- **`timeline` 버킷 인덱스가 저장 시간과 기준이 다르다.** 1분 이상 일시정지하면 그래프 x축 라벨이 건너뛴다. 수정 범위가 번져서 미뤘다
- **신규 가입을 막아 뒀다.** 웹캠을 다루는 서비스라 불특정 다수의 계정을 받지 않았고, AI 기능이 개인 API 키를 쓴다
